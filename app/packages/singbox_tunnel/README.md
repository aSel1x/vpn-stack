# singbox_tunnel

sing-box behind the app's `TunnelController`, on the two platforms that have an
engine: a `VpnService` on Android and a `NEPacketTunnelProvider` on iOS, each
establishing the TUN interface and handing its file descriptor to libbox.

Not in `app/android/`, because that directory is generated by `flutter create`
in CI and is gitignored — anything hand-added to it is deleted on the next run.
A plugin package is the seam that *is* committed, so every line of Kotlin lives
here. `app/ios/` is the exception at the other end: an app extension is a second
target and `flutter create` writes no such thing, so that directory is committed
and generated by `app/tool/ios_project.rb` — but the Swift still lives here, and
that project references it by path. One package holds both platforms' code and
the Dart that drives them.

## Three things this package does not do

**It does not build a sing-box configuration.** `SingboxTunnel` takes a
`SingBoxConfigBuilder` — `String Function(TunnelProfile)` — and hands whatever
it returns to the engine verbatim. `app/lib/config/` is the single definition of
that format; a second one here is the drift `app/README.md` refuses.

**It does not decide which platform it is on.** `app/lib/main.dart` wires it for
Android and iOS and `UnimplementedTunnel` everywhere else. Constructing
`SingboxTunnel` subscribes to its EventChannel immediately, so on a platform with
no implementation it reports `failed` at startup rather than quietly doing
nothing — correct, and still not what a macOS build should show.

**It does not branch on the platform, except in its words.** One Dart controller
drives both: the channel contract is five commands and one event shape, and
everything that differs is below it. What does differ is the prose in a failure,
and that is data — `TunnelPlatformText`, injected, defaulted from
`defaultTargetPlatform`. Every message used to name Android unconditionally, so
an iPhone whose tunnel would not come up was told to read `adb logcat` for a
service that had never existed on the device. A diagnosis naming the wrong
operating system is worse than a terse one: it sends somebody after an artifact
that cannot be there. Beyond the wording, a platform's own `PlatformException`
message is passed through **unwrapped** — both sides write prose naming what is
missing and what to do about it, and `TunnelStatus.message` is displayed as it
stands.

## Where the interface lives

`lib/tunnel_api.dart` **is** the app's tunnel interface, and it is here rather
than in `app/lib/tunnel/` because a Dart class can only implement a type it can
import and this package cannot import the app — `app -> singbox_tunnel -> app`
is a cycle pub refuses. That reasoning is the whole reason for the layout and it
does not expire.

The move is complete: `app/pubspec.yaml` carries the `path: packages/singbox_tunnel`
dependency, and `app/lib/tunnel/tunnel.dart` is one `export` line, so
`import 'tunnel.dart'` still resolves from every screen and from
`unimplemented_tunnel.dart`. While there were two copies of that interface,
`SingboxTunnel` implemented a *different* `TunnelController` than the screens
used, and the analyzer said so — 1,800 lines of plugin wired to no call site.

## The tests

`test/` covers the Dart half, and it is the only half a machine with no Android
SDK, no JDK and no macOS can judge at all:

```
cd app/packages/singbox_tunnel && flutter pub get && flutter test
```

It is a separate package with its own lock, so resolving it does not touch
`app/pubspec.lock`. `flutter test` run from `app/` collects `app/test/` and never
looks in here, which is why this directory needs its own step in
`.github/workflows/app.yml` — a test nothing runs is a test that will eventually
stop being true. `flutter analyze` from `app/` *does* reach these files, because
the analyzer walks the whole directory tree, which is why `flutter_lints` is a
dev dependency here: without it, a local `flutter pub get` in this directory
creates a package config that cannot resolve the `include:` in
`app/analysis_options.yaml`, and every rule in it silently stops applying while
CI still enforces them.

What the suite is about, throughout, is the one failure this client must never
have: reporting "Connected" with no tunnel up. `connected` is asserted to be
reachable *only* from a platform status that says so — not from `start`
returning, not from a timeout, not from an event shape this build cannot read,
each of which is a separate test with a fake platform behind a mocked
`MethodChannel` and an `EventChannel` the test drives by hand. The 45-second
connect window and the 20-second stop window are exercised on `testWidgets`' fake
clock, so they cost no wall time and still prove that expiry fails loudly.

## libbox.aar

sing-box publishes no Android library: the v1.14.0 release carries 167 assets
and not one `.aar`. The `libbox` job in `.github/workflows/app.yml` builds it
from source — it reads the version out of `compose.yml` so the client and the
server share an engine version, then runs `make lib_install && make lib_android`
— uploads it as the `libbox-<version>` artifact, and the `android` job
(`needs: [check, libbox]`) downloads it straight into
`android/libs/`, the directory `android/build.gradle` resolves `libs/libbox.aar`
against, and then asserts the file landed there.

`android/build.gradle` still refuses to configure when it is absent, which is
deliberate: with the library missing the module compiles, registers its channels
and produces an APK that dies at the first connect with a
`ClassNotFoundException` thrown from inside a Go callback.

The `.aar` is ~60 MB of built Go and is gitignored here: a build artifact, and
this repository is public. `Libbox.xcframework` is the same story on the Apple
side — built by `libbox_apple`, unpacked by `app/tool/unpack_libbox.sh`, never
committed. `ios/README.md` is the iOS half's own record.

## The libbox API this is written against

sing-box **v1.14.0**, read at that tag rather than remembered. v1.14.0 has no
`BoxService`; the host-facing entry point is a `CommandServer`, and the service
it manages lives behind gRPC:

| what | where |
| --- | --- |
| `Libbox.setup(SetupOptions)` | `experimental/libbox/setup.go:106` |
| `PlatformInterface`, 27 methods | `experimental/libbox/platform.go:5` |
| `CommandServer(handler, platform)` | `experimental/libbox/command_server.go:54` (`NewCommandServer`) |
| `CommandServerHandler`, 7 methods | `experimental/libbox/command_server.go:43` |
| `startOrReloadService(config, override)` | `experimental/libbox/command_server.go:199` |
| …which is synchronous | `daemon/started_service.go:250` — returns nil only once `instance.Start()` has returned |
| `closeService()` / `close()` | `command_server.go:214` / `:187` |
| `TunOptions` handed to `openTun` | `experimental/libbox/tun.go:18` |
| route ranges are precomputed | `experimental/libbox/service.go:66` → `sing-tun/tun_rules.go:109` |
| Java package `io.nekohasekai.libbox` | `cmd/internal/build_libbox/main.go:128` (`-javapkg`) |
| minSdk 24 | `cmd/internal/build_libbox/main.go:172` (`AndroidAPI: 24`) |

That synchronous start is the whole reason this package can report `connected`
at all. Nothing here reports it on a timer or on an assumption — and a
successful start is still not sufficient on its own: `instance.Start()` succeeds
for a proxy-only configuration, in which `openTun` is never called and no packet
is routed, so the platform side checks that it is holding a TUN descriptor
before it says the word.
