# singbox_tunnel

sing-box on Android, behind the app's `TunnelController`. A `VpnService` that
establishes the TUN interface and hands its file descriptor to libbox.

Not in `app/android/`, because that directory is generated by `flutter create`
in CI and is gitignored — anything hand-added to it is deleted on the next run.
A plugin package is the seam that *is* committed, so every line of Kotlin lives
here.

## Two things this package does not do

**It does not build a sing-box configuration.** `SingboxTunnel` takes a
`SingBoxConfigBuilder` — `String Function(TunnelProfile)` — and hands whatever
it returns to the engine verbatim. `app/lib/config/` is the single definition of
that format; a second one here is the drift `app/README.md` refuses.

**It does not decide which platform it is on.** Wire it only where it works:

```dart
final TunnelController tunnel = defaultTargetPlatform == TargetPlatform.android
    ? SingboxTunnel((TunnelProfile p) => encodeSingBoxConfig(
        buildSingBoxConfig(outbound: parseShareUri(p.importUris.first))))
    : UnimplementedTunnel();
```

Constructing `SingboxTunnel` subscribes to its EventChannel immediately, so on a
platform with no implementation it reports `failed` at startup rather than
quietly doing nothing. That is correct and it is also not what a macOS build
should show; `UnimplementedTunnel` still names what each other platform needs.

## Where the interface lives, and what has to change in the app

`lib/tunnel_api.dart` **is** `app/lib/tunnel/tunnel.dart`, byte-identical below
its header. A Dart class can only implement a type it can import, and this
package cannot import the app — `app -> singbox_tunnel -> app` is a cycle pub
refuses — so the interface had to move to the package side rather than be
depended upon from it.

Two edits in `app/` complete the move, and until they land there are two
definitions of one interface and the app cannot use this package at all:

1. `app/pubspec.yaml`, under `dependencies:`

   ```yaml
   singbox_tunnel:
     path: packages/singbox_tunnel
   ```

2. `app/lib/tunnel/tunnel.dart` becomes exactly one line:

   ```dart
   export 'package:singbox_tunnel/tunnel_api.dart';
   ```

   `unimplemented_tunnel.dart` imports `'tunnel.dart'` and keeps working; so
   does every screen.

A third is needed before an APK can be built at all — see below.

## libbox.aar

sing-box publishes no Android library: the v1.14.0 release carries 167 assets
and not one `.aar`. The `libbox` job in `.github/workflows/app.yml` already
builds it from source — it reads the version out of `compose.yml` so the client
and the server share an engine version, then runs `make lib_install && make
lib_android` — and uploads it as the `libbox-<version>` artifact.

Nothing downloads that artifact into `android/libs/libbox.aar` yet, and
`android/build.gradle` fails the build with that sentence rather than producing
an APK that registers channels and throws `ClassNotFoundException` from inside a
Go callback on first connect. The `android` job needs a `needs: libbox` plus a
`download-artifact` step into `app/packages/singbox_tunnel/android/libs/`.

The `.aar` is ~60 MB of built Go and is gitignored here: a build artifact, and
this repository is public.

## The libbox API this is written against

sing-box **v1.14.0**, read at that tag rather than remembered. v1.14.0 has no
`BoxService`; the host-facing entry point is a `CommandServer`, and the service
it manages lives behind gRPC:

| what | where |
| --- | --- |
| `Libbox.setup(SetupOptions)` | `experimental/libbox/setup.go:106` |
| `PlatformInterface`, 27 methods | `experimental/libbox/platform.go:5` |
| `CommandServer(handler, platform)` | `experimental/libbox/command_server.go:54` (`NewCommandServer`) |
| `CommandServerHandler`, 7 methods | `experimental/libbox/command_server.go:43` |
| `startOrReloadService(config, override)` | `experimental/libbox/command_server.go:199` |
| …which is synchronous | `daemon/started_service.go:250` — returns without error only when the start was not interrupted -- which is why this package does not treat that return as proof, and checks that a TUN descriptor exists before reporting connected.Start()` |
| `closeService()` / `close()` | `command_server.go:214` / `:187` |
| `TunOptions` handed to `openTun` | `experimental/libbox/tun.go:18` |
| route ranges are precomputed | `experimental/libbox/service.go:66` → `sing-tun/tun_rules.go:109` |
| Java package `io.nekohasekai.libbox` | `cmd/internal/build_libbox/main.go:128` (`-javapkg`) |
| minSdk 24 | `cmd/internal/build_libbox/main.go:172` (`AndroidAPI: 24`) |

That synchronous start is the whole reason this package can report `connected`
at all. Nothing here reports it on a timer or on an assumption.
