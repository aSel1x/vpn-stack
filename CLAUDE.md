# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal VPN server plus the CLI that operates it. Four protocols, one user database, one command surface:

- **`sing-box`** — VLESS+REALITY (`10443/tcp`) and Hysteria2 (`20443/udp`), the everyday path.
- **`hwdsl2/ipsec-vpn-server`** — IKEv2 / L2TP/IPsec / Cisco IPsec (`500`, `4500`, `1701` udp).
- **`dnstt` + `dnstt-sshd` + `dnstt-socks`** — DNS-tunnel last resort (`53/udp`), for networks that allow nothing else. One shared tunnel, **a login per person**: the Noise key belongs to the server and encrypts the transport before anyone authenticates, so it cannot be personal, but the sshd behind it can. That is what makes `user rm` and `user disable` cut dnstt access at all — with one shared account, removing somebody left their tunnel working and nothing to revoke. Verified: after a `disable`, that person's own password is refused while everyone else's still works.

  The logins are rendered from `users.json` into `rendered/dnstt-sshd/logins` and created at container start, so `/etc/passwd` is rebuilt from the list every time and a removed account cannot linger. The cost is that changing the user list recreates the container and drops live dnstt sessions, the same way it already does for IKEv2 — and that recreation is **load-bearing, not incidental**. The entrypoint's account loop is `id "$name" || adduser`: it only ever *adds*. Nothing deletes an account that dropped out of the list, so the reset comes entirely from the container being new. `composectl._CONSUMERS` therefore classifies `dnstt-sshd/` as `RECREATE` even though the logins file is a plain bind mount. It was briefly classified as `MOUNT` — a `restart` — and that reuses the writable layer, so a removed user kept their account, their group and their password hash while `AllowGroups tunnel` still let them in: `user rm` reported success and revoked nothing. A user created before the field existed has no `dnstt_password`, gets no login, and `render` says so on stderr. There is deliberately no migration command for a one-record problem: set the field in `users.json` or re-add the user. `render` must not mint it (it is pure, and `apply` would be handing out a password nobody had been told), and `load` must not (that rotates a live credential on every read).

  **`dnstt.render` refuses an empty login list, and that refusal is safe where the missing-zone one is not.** `entrypoint.sh` exits 1 on a list with no logins — an sshd with zero accounts looks healthy and answers nobody — and `restart: always` then crash-loops it invisibly: that sshd binds loopback only, so it contributes no port to `composectl.wait_ready` or `scripts/smoke.sh`, while `dnstt-server` keeps answering `53/udp` into a tunnel whose far end refuses every login. So `render` raises and the candidate tree is never promoted, which costs the operator one sentence instead of an evening. What makes raising safe *here* is that every route out of it writes `users.json` before it applies — `user add`, `user enable`, setting the field by hand — and `protocol off dnstt` does not render dnstt at all, so the refusal cannot block its own fix. The missing zone is the counter-example and the sharpest one in this repo: raising on it **bricked a server**. `protocol on dnstt` had already written dnstt into `state.json`, so `apply`, `user add`, `deploy` and the systemd boot unit all exited 1 together, with `users.json` diverging from the served config and no command left that could put it back. That one is a warning on stderr, and the hard refusal lives at `protocol on`, which is the last point that can still roll the toggle back. `scripts/smoke.sh` is what covers the gap a warning leaves — the boot unit has no stderr anybody reads — by asking the *running* container what it serves, parsing `docker inspect`'s argv rather than indexing it: a dropped zone makes argv one shorter, so `cmd[-2]` silently becomes `/keys/server.key`, which has a dot in it and passes any domain-shaped test.

  The container refuses to start at all on a login name that collides with an account its base image ships. The loop only ever adds, so for `mail`, `root`, `sshd`, `ftp` or any of the rest the `id` succeeded, the `-G tunnel` grant was skipped, `AllowGroups` then refused the login — and the `chpasswd` that followed ran anyway and set that *system* account's password to the person's dnstt password. Measured against the old file: a user named `mail` came out with a real hash in `/etc/shadow`, a group list of `mail` alone, and no way in. The list of accounts to refuse is snapshotted at build time into `/etc/dnstt-sshd.reserved` rather than read from `/etc/passwd` at run time, because once the writable layer has been written to once, `/etc/passwd` cannot tell a baked-in system account apart from one a previous start created — and that difference is exactly what decides whether a name is a collision to refuse or a login to reuse. The whole list is validated before a single account is touched: this container's entire revocation story is `/etc/passwd` being rebuilt from that file, so a list it cannot serve faithfully is not one to serve partially. `users_store.validate_name` rejects the same names at the source, which is where the fix belongs; the entrypoint is the depth, because the file can arrive from a restore, a hand edit or a rolled-back tree that validator never saw. Group membership is also *asserted* on every start rather than assumed — `adduser -G` grants it only on the run that creates the account, so a plain `docker restart` left sshd refusing logins and logging nothing that named the cause.

  Off by default; `protocol on dnstt` builds the image and has `dnstt-server -gen-key` mint the Noise keypair, because that format is the binary's own. The zone is **deployment config, not a constant**: set `VPN_DNSTT_ZONE=<your delegated zone>` in `/etc/vpn-stack/.env`, which `compose.yml` interpolates into the dnstt command. Python reaches it without breaking the pure seam: `render.snapshot()` folds it into the `Secrets` snapshot under `dnstt.zone`, so `render` and `share` stay functions of their arguments. Held in a module global read at import instead, `share()` raised for exactly the caller purity exists for. It was hardcoded here and repeated verbatim in `compose.yml` until a stranger cloning this repo would have served the author's zone, with their clients resolving a domain somebody else controls. `compose.yml` uses the bare `${VPN_DNSTT_ZONE}` form and **not** `${VPN_DNSTT_ZONE:?}` — measured on Compose v5.3.1, the `:?` form fails *project load* even when dnstt's profile is inactive, which is the same trap `ikev2.env` already documents.

  The decoded stream exits into an sshd **in a container**, not the host's. iOS clients speak DNSTT→SSH and need a login; on the host that would be a real account plus an `/etc/ssh/sshd_config` edit, neither captured by `vpn backup` and both to be redone after every rebuild. The container listens on loopback only and admits one account per enabled user, gated by `AllowGroups tunnel`. (It did allow exactly one, shared; that is the arrangement this replaced, and the sentence outlived it.) `PermitOpen` is **`any`**, and a list is not a workable alternative: the clients use SSH *dynamic* forwarding, so every site is a fresh destination. The log proved it twice — 17 refusals of `1.1.1.1:853` (they resolve over DoT through the tunnel before opening anything), then, once that was allowed, refusals of twenty-odd web hosts on `:443`. `microsocks` is never touched by this path; it stays for the laptop variant. This concedes less than it looks: the other three protocols already give unrestricted access to whoever holds their credentials, and what keeps this safe is the credential's blast radius — random password, loopback-only sshd, one route in, and that route already requires the pinned Noise key. Its host key lives in a volume so it does not change under clients on restart, and `vpn backup` carries that volume for the same reason.

  All three images are pinned, and that matters more here than general hygiene: `composectl.up` passes `--build`, and `apply` runs from `user add`, `user rm`, `protocol on`, `protocol off`, `deploy` and the boot unit — so an unpinned input is re-resolved on a live server at a moment nobody chose, unattended, whenever the BuildKit cache misses. `dnstt-server` is a version (`v1.20260501.0`), `microsocks` is a **commit** rather than a tag, and both base images are multi-arch index digests so the pin still resolves on another architecture. The microsocks build fetches the tag and then asserts the sha, so a *moved* tag fails the build loudly instead of quietly substituting something else. Each image carries its resolved version as an `org.opencontainers.image` label, so `docker inspect` answers "what is running" on a box whose checkout has since moved. `dnstt-socks` runs as uid 10300 with an empty capability set and a read-only rootfs (it binds one high loopback port and opens outbound sockets, so it needs nothing); `dnstt-server` keeps `NET_BIND_SERVICE` and nothing else, because it binds `udp/53` in the host's namespace, and is read-only too. `dnstt-sshd` keeps root and its writable filesystem, and that is argued rather than assumed: it rewrites `/etc/passwd`, `/etc/shadow` and `/etc/group` from the rendered list on every start, generates the host key into the volume, writes `sshd_config`, and then sshd needs root to set*id into each session. The two loopback-only services have healthchecks, because `restart: always` made a container that starts and exits indistinguishable from a healthy one and these are the two whose failure nothing else can see; they report and nothing more, since compose does not restart on health.

  `-gen-key` prints both halves as hex on stdout, and that is what `prepare()` parses. Writing them with `-privkey-file` into a bind mount produces root-owned files that nothing but root can read back, and a temp directory that then fails to clean up.

A deployment is a checkout at `/opt/vpn-stack` and state at `/etc/vpn-stack`; the target itself lives in `.vpn-host` (gitignored) or `VPN_HOST=`, never in the tree.

## Where things run

**`./vpn` on your machine. `vpnctl` on the server. Never the reverse.** There is now a third operator — the Flutter client, which holds root SSH to the same box and runs the same `vpnctl` over the same lock. See "The app".

`./vpn` is a stateless bash wrapper at the repo root. It holds no config, no cache, no secrets: anything it doesn't recognise is forwarded verbatim over SSH to `vpnctl` on the server, under `flock /run/vpn-stack.lock`. The server is the only place that touches Docker, iptables, ufw and the user database.

```bash
./vpn status                       # what the server is running
./vpn user add <name>
./vpn user export <name> --qr      # ASCII QR in YOUR terminal
./vpn protocol list | on <x> | off <x>
./vpn deploy                       # sync code, validate, converge
./vpn smoke                        # assert it is actually serving
./vpn backup f.age                 # encrypted here, never on the server
./vpn restore f.age                # onto a rebuilt box
./vpn init root@<ip>               # bare Ubuntu -> serving VPN, one command
```

Set the target once with `.vpn-host` (gitignored) or `VPN_HOST=`; the key with `VPN_SSH_KEY=` (it lives in `~/.ssh/`, never in this tree).

**`/run/vpn-stack.lock` is the entire multi-operator story, and `vpnctl` takes it itself.** Two writers that read-modify-write `users.json` or `state.json` lose one of the two writes, and two `apply` runs promote each other's candidate tree — which is the one thing the atomic promote downstream cannot save you from. Every wrapper takes it today — `./vpn`, `scripts/deploy.sh`, `scripts/install.sh`, `scripts/provision-host.sh`, the boot unit and the app — but four server-side callers invoked `vpnctl` bare while this file already described the arrangement as complete. So correctness stopped being a property of each caller and moved inside. `cli._lock_if_mutating` locks the commands that write and leaves the readers alone — `status`, `user list`, `user export` and `protocol list` take nothing, because a reader that could fail during an apply would leave nobody able to *observe* the apply, and the app polls `status` in exactly that window.

That inner lock has to be non-blocking, and the reason is measured, not assumed: `flock(1)` inside `flock(1)` on the same path from a child process opens a second file description, which the kernel treats as a different holder, so a blocking inner lock waits for one its own parent will never release. `timeout 3 flock LK bash -c 'timeout 2 flock LK echo INNER'` prints nothing. **`VPN_STACK_LOCK_HELD=1` is the handshake** every wrapper exports so the inner lock stands down, and `LOCK_NB` is the second line of defence, so a caller that forgets the handshake gets a refusal instead of a process that never returns. A lock conflict exits **75** (`EX_TEMPFAIL`), which is what `flock -E 75` in the app's wrapper already reserves for "somebody else is mid-apply" — so a client can tell busy from broken without reading English. On a box with no `/run` to lock (a dev machine, the test suite) it warns and runs unserialised rather than failing, because there is no live state there to serialise against.

**`vpnctl` refuses to mutate anything off-server** (`vpnctl/guard.py`). Before that guard existed, `vpnctl user add` on a laptop did not fail — it *succeeded*, rewriting a local copy of live credentials and starting a real sing-box bound to the laptop's ports.

`VPN_STATE_DIR=<dir>` is the test escape hatch, and it moves the whole blast radius, not just the Python: `apply` renders and validates but **does not converge** under a pointed state directory, because Docker, ufw and the host's ports are not relocated by an env var. Otherwise the escape hatch reproduced the exact bug the guard exists to stop, one level down. `VPN_ALLOW_CONVERGE=1` overrides.

There is no fallback to the repo directory any more. If `/etc/vpn-stack` is not there, this is not the server and `vpnctl` says so, instead of quietly writing live credentials into a checkout.

## Secrets live outside the repo

`/etc/vpn-stack`, mode 0700, root-owned:

```
/etc/vpn-stack/
├── secrets/        0600 each: reality.{key,pub}, reality.short_id, hysteria2.{crt,key,obfs},
│                   ipsec.{psk,primary_user,primary_password}, dnstt.server.{key,pub}
├── users.json      who has access, across every protocol
├── state.json      which protocols are on; revoke_pending; converge_pending; last_applied
├── .env            VPN_SERVER_HOST (the repo's ./.env is a symlink to this,
│                   because docker compose reads .env from the project directory)
├── data/           sing-box runtime state
└── rendered -> rendered-<ts>-<rand>/   generated config, atomic symlink
```

Keeping them here means no *generated* credential is ever written into the checkout, and `rsync` cannot clobber a live key. `users.json` is written through a temp file created at 0600 and `os.replace`d, so an interrupted write cannot leave an empty user database or a world-readable one; the keyring, the rendered candidate tree and **`state.json`** are written the same way, and a zero-length file is not counted as a secret (otherwise `bootstrap` would skip regenerating it).

`state.json` was the exception until recently — a plain `write_text` followed by a `chmod`, so the mode was set after creation and a truncated write was perfectly possible — and it is the file holding the two intents that have to outlive the command that formed them. Losing it entirely is survivable and loud; losing its *contents* is neither: a `revoke_pending` nobody can read is a certificate that stays valid after a `user rm` reported success, and a `converge_pending` nobody can read is sing-box serving the old keys with every port bound and `smoke` green. Its `load()` had no error handling at all, so a truncated file raised `JSONDecodeError` out of every command including `status` — not one broken command but a server with no working command surface, reporting a traceback that named neither the file nor the remedy. It now refuses a schema newer than the code by name, exactly as `users_store` does (`users.json` is at `SCHEMA_VERSION` 2, the version that added `dnstt_password`). A *missing* `state.json` still returns the default set, because a freshly provisioned box genuinely has none — but silently that default has dnstt **off**, so the next `apply` would remove its three containers and delete `53/udp` from ufw as if the operator had asked, and the protocol that ships off is also the last-resort one. `load_or_default()` reports which of the two happened; `load()` is unchanged for every caller that does not care.

**That is not the same as "a clone cannot contain a credential", which this file used to claim and which was false.** Nothing stops an *operator* from putting one there, and `README.md` used to tell them to: `./vpn backup > vpn-$(date +%F).age` from the repo root. One such tar — the whole state directory plus the IKEv2 volume, so every secret, every user's password on every protocol, and the CA private key, under one passphrase — was committed and pushed. (No hash here on purpose: that commit no longer resolves, because `git filter-repo` has since run. `git rev-list --objects --all` finds no `.age`, `.p12`, `.mobileconfig`, `.sswan` or key-shaped blob reachable from any ref.) The durable half of the fix is `.gitignore`, which now carries `*.age`, `*.p12`, `*.mobileconfig` and `*.sswan` **extension-wide** rather than by exact path, and a README that points at a directory outside the tree.

`.gitignore` is load-bearing where the *operator* is the one who can put a credential in the tree, and it no longer pretends to be anything else. It used to carry three rules protecting paths that do not exist — `sing-box/vless-reality/` and `sing-box/hysteria2/`, the two fragment directories of the old three-sibling layout, and `scripts/.deploy_key*`, which nothing mints now that CI holds no secrets and `install.sh` pushes rather than clones. All three are gone, and the file says why in place of them: nothing renders a credential into this tree, because `render` writes only into `/etc/vpn-stack/rendered-<stamp>-<rand>/` at 0600 under a 0700 parent. **An ignore for a path nothing ever creates is an invariant a reader cannot verify from the file, and this document was citing one of them as live protection** — describing `dnstt/keys/*` as carrying a `!server.pub` exception it never had. That rule itself stays, and stays checkable: `dnstt/SETUP.md` § 2 is where `dnstt/keys/server.key` is discussed as a path a reader might create by hand with `dnstt-server -gen-key -privkey-file`, so grep the document for it and the rule has something to point at. Directory-wide, with no allowlisted exception, so a second file dropped beside the key is covered too. What the stack does itself never lands there: `protocol on dnstt` parses `-gen-key`'s stdout and stores both halves in the state directory. `push.sh` rsyncs with `--filter=':- .gitignore'`, so this file also decides what a deploy sends.

Backups: `./vpn backup` tars `/etc/vpn-stack` **and both** of `compose.yml`'s named volumes, from one list read by `backup` and by `restore` (the ikev2 name used to be written out in both, which is how a two-entry list ends up updated in one place). `vpn-stack_ikev2-vpn-data` holds `cert9.db`/`key4.db`, the NSS database with the IKEv2 CA private key — omit it and every certificate this server ever issued is unrecoverable. `vpn-stack_dnstt-sshd-keys` holds the dnstt SSH front's host key, which is in a volume precisely so it does not change under clients; omit *it* and a restore onto a rebuilt box mints a new one and hands every dnstt client a changed-host-key warning indistinguishable from an attack, for the one protocol whose users have no fallback. `restore` tolerates a backup taken before that member existed, and says so rather than passing over it in silence. The stream is encrypted by `age -r` on your machine, to the identity `./vpn backup-key` writes at `~/.config/vpn-stack/backup.key` (override with `VPN_BACKUP_KEY`); the key never reaches the server.

**"The plaintext never lands on either disk" was this file's claim and it was false.** The server half built its two intermediate tars with plain shell redirection into `/tmp` at root's umask — mode 0644, in a world-traversable directory — and under `set -e` the `rm -f` ran only if the final `tar c` succeeded. Break the pipe (the local `age` dies, the ssh drops, somebody Ctrl-Cs) and both files persisted indefinitely at a predictable path: every user's password on every protocol, the REALITY private key, and the NSS CA private key, readable by any account on the box. That this was an oversight and not a trade-off is provable from the same file — `restore`, twelve lines below, already did `umask 077`, `mktemp -d` and a trap. The backup half now does all three, and traps `HUP INT TERM` as well as `EXIT`, because when the far end goes away sshd HUPs that shell and an untrapped HUP skips the `EXIT` trap — which is exactly the broken-pipe case the files used to survive. A temp directory is still needed at all because `tar` writes each member's size into its header, so a member has to exist in full before it can be streamed. The honest claim is therefore: the identity never reaches the server, the plaintext never touches *your* disk, and on the server it exists for the length of the transfer inside a 0700 directory a trap removes.

Prefer `./vpn backup <file>` to `./vpn backup > <file>`. The redirect is the *shell* truncating the destination before ssh has said a word, so a backup that fails half way has already destroyed the last good one — and the occasion you find that out is a rebuilt box. Given a path, `backup` writes `<file>.partial`, renames only once `age` has exited 0, and removes the partial otherwise: a truncated `.partial` is indistinguishable from a backup by anything except `age`.

The encryption used to be `age -p`, and the whole security of every secret on the box plus the IKEv2 CA key was then one passphrase a human had to be able to type — which is also why one committed `.age` was an incident rather than a shrug. An identity is high-entropy by construction and never typed. The trade-off points the other way and has to be said out loud: a passphrase cannot be lost with a laptop, so that file belongs in a password manager, and `backup-key` refuses to replace an existing one because every backup already taken is encrypted to it. `restore` sniffs the age header — `-> scrypt` means the old passphrase scheme — so backups from before the change still restore with no flag. The sniff uses `grep -a`: the header is ASCII but the payload after it is not, so without it grep calls the stream binary, exits 1 without looking, and sends every passphrase-era backup down the identity branch to fail on a rebuilt box — the only occasion anyone runs restore. `rendered*` is excluded from the tar — the symlink and every generation behind it. All of it is derived, and `apply` rebuilds it.

`./vpn restore` is the other half, and it has been exercised: restoring the stream into a clean directory reproduced every secret bit-identically, brought `cert9.db`/`key4.db` back into the volume, and regenerated a client's VLESS URI **byte-identical** to the one issued before. It refuses to run against a server that already has users unless you pass `--force`, and stops `ipsec-vpn-server` first, because `pluto` holds the NSS database open.

## The protocol registry

`vpnctl/protocols/` — one module per protocol, each exporting a single `Protocol`. It owns everything protocol-specific: ports, required secrets, how to render config, how to build a share link, whether it is a sing-box inbound or its own container.

A `ShareItem` is one of three shapes, and picking the wrong one is not cosmetic: a `uri` gets a QR code and a tappable link, a `filename` gets a download, and `fields` get a form to copy by hand. DNSTT-over-SSH has no import format at all — no URI scheme, nothing to scan — so its settings were crammed into a `uri` and every layer duly treated them as one, producing a QR nothing could read and a link that imported nothing. Hence `fields`. Exactly one shape is enforced in `__post_init__`, where the traceback names the protocol module rather than the renderer: every layer above branches on which field is set and the branches are *ordered*, so an item in two shapes is not ambiguous in theory, it is silently the wrong one of the two.

The `filename` shape has a producer nowhere in the pure layer today — IKEv2's bundles bypass it because `ikev2.sh` makes them inside the container — and, more to the point, **no consumer**: `cli.cmd_user_export` prints `uri`, then `fields`, and drops anything else without a word. A protocol that starts returning a filename-shaped item has to add that branch in the same change, or `user export` reports `ok` while the one file the recipient needed is simply absent from the payload.

```python
render(secrets, users) -> {relative path: bytes}      # pure
share(secrets, user, host) -> [ShareItem]             # pure
bootstrap() -> {secret name: bytes}                   # cheap, at install time
prepare()   -> {secret name: bytes}                   # optional, expensive
```

**`share()` must not need a private key.** `vless_reality.share()` used to derive the REALITY public key from `reality.key` on every call, so the pure seam the app renders links through would have meant shipping the private X25519 key to a phone. `bootstrap()` now stores the derived `reality.pub` beside it — public halves in the keyring is established practice here, `dnstt.server.pub` was already one — and `share()` prefers it, falling back to deriving it only for a keyring made before the field existed. `reality.pub` is deliberately **not** in `secret_names`, or an existing server would fail to render.

That change forced a second one. `bootstrap_keyring` used to skip per *secret name*, so on a server that had `reality.key` but no `reality.pub` a plain `bootstrap` would mint a whole new keypair, skip the existing private half, and write the **new** key's public half — every share link silently unusable afterwards. The same latent bug already existed for hysteria2: losing `hysteria2.key` alone made bootstrap mint a fresh key that did not match the surviving `hysteria2.crt`. So the skip is now **per protocol**: a half-present set is refused and named rather than topped up, because filling the gap pairs a fresh half with a stale one, which renders, serves, and fails on every client. Restore the missing file, or `--force` the whole set.

There is exactly one carve-out, and it is as narrow as the reason for the refusal. `reality.pub` is a deterministic function of the private half sitting beside it — not a new credential, the same key's other face — so filling *that* gap leaves every issued profile working. A protocol declares which of its bootstrap outputs are **derivable** on its own `Protocol`, beside the `bootstrap()` that mints the pair, so the derivation and the minting cannot drift; a derivation that raises leaves its gap a gap, because the material it reads being missing is a damaged keyring and the refusal already knows how to name one. Without this the "`share()` never touches the private key" invariant was unreachable on any server bootstrapped before that field existed: no command could add the file, and `--force` meant reissuing every profile ever handed out.

The refusal is a **typed error**, `bootstrap.KeyringRefused`, carrying the refused protocols as data. It used to be a sentence folded into the message `bootstrap_keyring` returned, which still returned `True` whenever some *other* protocol's keys had been written — so the boolean answered "did anything get written", which is not the verdict, and the CLI recognised the one outcome that demands a decision by matching the literal prefix `"NOT refilled:"` out of English prose. Reword that sentence without touching the constant and `bootstrap` goes quietly back to exiting 0 on a keyring it refused to complete. It now reaches the same `main()` handler as `RenderError`, `MissingSecret`, `UsersError` and `StateError`, so `apply` gets the same sentence and the same exit code for free.

`prepare` exists for one reason: dnstt's Noise keypair is the `dnstt-server` binary's own format, so producing it means building a Go image. Doing that in `bootstrap` would make every fresh server pay ~800 MB for a protocol that ships disabled. It runs at `protocol on` instead, and a failure rolls the toggle back — leaving it enabled with no key would make every later `apply`, including the one systemd runs at boot, die on a missing secret with no clue how it got there.

`render` and `share` are pure — no `open()`, no `subprocess`, no globals. That is deliberate and load-bearing: it is the seam a client renders share links through with no server round-trip. Keep it that way. (The registry's own docstring still calls that client hypothetical; it is not, see "The app".)

**`render` validates the names it is handed, not the ones `user add` wrote.** Name validation at `user add` covers what `user add` creates; `render()` is handed whatever `users.json` actually holds, and a hand edit, a restore from an older backup or a stale checkout rsynced over a newer database can put anything there. That matters because `render_ikev2_env` emits `VPN_ADDL_USERS` and `VPN_ADDL_PASSWORDS` as two **space-separated** lists zipped back together by position inside the image, so one whitespace name makes them different lengths and hands every later user somebody else's password — on a config that renders, validates and serves. `ikev2.render` and `dnstt.render` both raise `RenderError`, so the candidate tree is never promoted; both use the whole shared validator rather than "the characters that break this file", so there is one definition of a renderable name. `ikev2.render` also refuses an L2TP password containing whitespace, from the other side of the same pairing. Every message names the user and the remedy and none of them ever names the credential. The remedy stays reachable because `user rm` writes `users.json` *before* it applies, so the command that fixes this is not blocked by it. `dnstt.render` makes the same check for its own file format, where a colon or a newline in a name silently becomes a different account — or two, with the password cut at the colon.

**sing-box logs at `warn`, and that is a decision rather than a default.** At `info` every connection line carries the authenticated user name beside the client's source address and the destination host, and compose gives every container a rolling `10m × 3` json-file — so the server kept a standing record correlating person ↔ residential IP ↔ site visited, on a box whose entire stated threat model is a network operator who inspects traffic. Nothing machine-readable depended on those lines: neither `vpnctl` nor `scripts/smoke.sh` parses sing-box's output, both assert on bound non-loopback ports, and `./vpn logs` only tails for a human. What it gives up is real and one-directional: a client that cannot connect now leaves almost nothing behind, so `./vpn logs sing-box` is thin and a handshake failure is diagnosed from the client's side or by raising the level for the length of one test and putting it back. The level lives in `sing-box/common/00_base.json`, which is JSON and has nowhere to say any of this, so the reasoning is in the registry's docstring where a reader actually meets it.

**The Hysteria2 link carries two pins, and they hash different things.** `pinSHA256` is the hysteria2 convention and hashes the whole DER certificate; sing-box's only pinning field is `tls.certificate_public_key_sha256`, which hashes the SubjectPublicKeyInfo and base64-encodes it — a different preimage in a different encoding, not convertible from one to the other. So a client built on sing-box could do nothing with the pin this server had been publishing, and its two options were to fail the handshake or to accept any certificate at all. `share()` emits both as `pinSHA256` and `spki`; other clients read the first and ignore what they do not know. Adding the second was a **client-visible change to the URI**, which is why the app's own value-level fixture is generated from `share()` rather than hand-typed — the last time it was hand-typed, `spki` was added and the Dart list stayed as it was, so every test passed while the parser refused every real link. Neither pin is a secret: both are functions of a certificate handed to anyone who connects, and no private half enters the computation, which is why they are computed rather than stored — the *opposite* of `reality.pub`, and for the mirror-image reason.

That certificate now carries `subjectAltName` and `basicConstraints`. It had **no X.509 extensions at all**, so there was no SAN for RFC 6125 name matching to match (the CN stopped being a name source a decade ago) and nothing saying the leaf is not a CA — leaving every client the same two options, pin or switch verification off, and "off" is the one people reach for first. Forward-only by construction: `bootstrap` does not re-mint a set that is already present, so an existing server keeps the exact certificate its clients pin and no profile has to be re-exported.

**Adding a protocol is a new module plus one line in `PROTOCOLS`. It changes no command line.** The `-C` directory list that used to be hardcoded in three places is gone: everything renders into one directory.

Four things verified against the real binaries, which the design depends on:

- **Two files in one `-C` directory concatenate their `inbounds`.** So the old three-sibling layout bought exactly one thing (drop a protocol by dropping a flag) and cost a triply-duplicated list. Now: `-C /etc/sing-box`, permanently. `certs/` sits inside that directory because `-C` merges `*.json` and does **not** recurse.
- **`sing-box check` exits 0 on two inbounds sharing a `listen_port`.** It catches a duplicate *tag*, not a duplicate port. `protocols.assert_ports_disjoint` exists because of this and is not decorative.
- **`docker compose up -d --remove-orphans` does not stop a service whose profile was deactivated** (Compose v5.3.1, still true on v5.5.1). Explicit `docker compose rm -sf <service>` does. `composectl.down_disabled` diffs and removes explicitly — relying on `--remove-orphans` would mean "protocol off" leaves the protocol serving traffic.
- **Compose resolves `env_file` when it loads the project, not when it starts the service.** `ikev2.env` only exists while ikev2 is on, so a plain path there made *every* compose command fail the moment you turned the protocol off — including the ones that bring sing-box up, and including the `rm -sf` meant to stop ikev2 itself. It uses the `required: false` long form. Verified by turning the protocol off and back on.

**Every image is pinned, pulled or built.** sing-box by tag (`ghcr.io/sagernet/sing-box:v1.14.0`) and `hwdsl2/ipsec-vpn-server` by digest, because `ikev2ctl` hard-codes that image's CLI contract — `--addclient` / `--deleteclient` / `--revokeclient` / `--exportclient` and the absence of `--removeclient` — so an unpinned tag means an upstream change silently breaks user management on the next pull. The three dnstt services are built rather than pulled, so what they are pinned *to* lives in each `Dockerfile` as an `ARG`: `dnstt-server` at a version, `microsocks` at a commit, both base images at their multi-arch index digests, each carried into the image as an `org.opencontainers.image` label. That is deliberately **not** restated in `compose.yml`, for the same reason `scripts/check.sh` reads the sing-box tag **out of compose.yml** rather than restating it: two literals drift, and the drift is invisible — the config validates against one binary and is then served by another.

This file used to flag the dnstt trio as a live unresolved hazard, and it was one: `go install …@latest` and `git clone --depth 1` of whatever HEAD happened to be, re-resolved by a `--build` that runs from `user add`, from `deploy` and from the boot unit. What closed it is worth stating precisely, because the pin is more than a version string — the microsocks build fetches the tag and then *asserts* the sha, so a moved tag fails the build loudly rather than silently building something else, which is the substitution the pin exists to stop.

## The apply pipeline

`vpnctl apply` is the only thing that changes the server:

1. Render the whole config into `rendered-<ts>-<rand>/` **beside** the live tree.
2. `scripts/check.sh` validates that candidate in a throwaway container.
3. On failure: delete the candidate, exit 1. **The live tree was never touched, so there is nothing to roll back.**
4. On success: `os.replace` the `rendered` symlink — atomic, so a reader sees the old tree or the new one, never a mixture.
5. Converge: bring up the enabled set, explicitly remove the disabled set, **wait for every expected port to bind**, ask docker which expected services are not running, reconcile ufw, reconcile the IKEv2 FORWARD rules and certificates.

The candidate's name carries a random suffix, not the timestamp alone, and `write_candidate` **refuses outright to `rmtree` the live tree**. Stamps are at one-second resolution and this used to delete whatever already had that name before rendering into it — so two applies inside the same second (a scripted `user add` loop, a deploy racing the boot unit) had the second one delete the tree the first had just promoted and two running containers were mounted from. The stamp stays in the prefix because `prune` orders generations by name, `.gitignore` and `vpn backup` both match `rendered*`, and a human reading the state directory needs to see when each was built.

**Converge bounces only what changed.** `composectl.changed_services` diffs the promoted tree against the candidate and maps each rendered path to the service that consumes it, and to *how* it reaches that process — `MOUNT` (bind-mounted; Docker re-resolves the mount source on start, so `restart` lands it) or `RECREATE` (only a new container will do). Before this, every `user add` unconditionally `--force-recreate`d everything, so adding one person dropped every live session on the box. The table is written by hand because `docker compose config` can only answer half of it — the volumes are in there, the `env_file` provenance is not.

Two failure modes this design has to keep closed, both of which it fell into once. First, **`up -d` alone does not restart a container whose bind-mounted file changed** but whose service definition did not — so dropping the flag without replacing it with a restart means config that silently never applies, which is worse than the downtime it saves. Second, a `RECREATE` service classified as `MOUNT` is a *revocation* bug, not a latency bug: see dnstt-sshd above. When in doubt, `RECREATE`; the cost is seconds of downtime, and the cost of the other mistake is a credential you believe you revoked.

Because the diff compares trees rather than asking what a container is *running*, a tree promoted without converging has to leave a mark that outlives the command — the same reasoning as `revoke_pending`. `bootstrap --force` and `apply --no-restart` both promote without bouncing, and without that mark the next `apply` would see an unchanged tree, bounce nothing, and leave sing-box serving the old keys forever while `smoke` passed because the ports were bound.

**`converge_pending` is now set for every promote-without-converge, not only those two doors.** It used to be written in exactly one place — inside the `--no-restart` branch — so every other exit between the symlink swap and the clear left no mark at all, and there is a third door, the only one that opens by accident: **a converge that dies after the swap.** `composectl.up` fails part-way by design, service by service, with sing-box last in sort order and therefore the usual stale victim. The operator's retry then rendered a byte-identical tree, diffed it to `{}`, bounced nothing, passed the readiness wait *because the old containers still held the ports*, and printed "config unchanged; nothing restarted" followed by "OK." with exit 0. `smoke.sh` was green. The mark now goes down immediately after `promote`, so any exit from there on — a `die()`, a Ctrl-C, an SSH drop during a long `--build` — forces the next apply to recreate everything; and exactly one thing lifts it, a converge that reported every step. The readiness wait is deliberately part of that: a port that never bound means the convergence did not finish, so it alone keeps the mark down among the warn-only steps, while a teardown or firewall failure does not — neither is a claim that the containers are running the wrong tree.

**Everything after `up` warns and exits 0, and the reason is the boot unit.** `vpn-stack.service` depends on that exit code, so the status cannot carry a teardown failure, a port that never bound or a firewall that would not reconcile. What makes that safe is that the verdicts are machine-readable instead of English prose a caller had to pattern-match: `apply --json` carries **`ports_ready`**, **`teardown_ok`**, **`firewall_ok`**, **`forwarding_ok`** and **`not_running`** beside the human text, `apply` refuses to print "OK." when any of them failed, and `_reconcile_ikev2_forwarding` always records its verdict rather than omitting the key when the container is down — because "not applicable" and "succeeded" read identically as an absent key.

**A bound port is not health**, and `composectl.not_running` answers the question a bound port cannot. `dnstt-server` holds `53/udp` while the sshd behind it crash-loops on loopback, where nothing probes it — so converge's only gate reported success on a protocol whose every client completed a tunnel to a closed door. `None` is kept distinct from the empty list throughout: "docker could not tell" is not a clean bill of health, and reading it as one is how `protocol off` once reported success while the protocol kept serving traffic.

The readiness wait matters: `docker compose up` returns immediately but `hwdsl2/ipsec-vpn-server` needs ~30s to bind, and much longer on its *first* run, when it also builds the NSS database and issues the CA. Without the wait, the smoke test that runs next fails on a server that is merely still starting — a false alarm that teaches people to ignore smoke tests.

"Bound" means bound on a non-loopback address, in both `composectl` and `scripts/smoke.sh`. Substring-matching the port number reports dnstt's `53/udp` as served on any stock Ubuntu, because `systemd-resolved` holds `127.0.0.53:53`.

**A deploy is not an install.** `deploy.sh` updates code on a server that `init` already provisioned; it checks for `vpnctl`, `/etc/vpn-stack` and `uv` *before* the rsync and stops with that list if any is absent. Against a rebuilt box it used to rsync the code and then die on `uv: command not found`, exit 127, explaining nothing.

`scripts/check.sh` is the single definition of validity. `scripts/push.sh` is the single definition of *what gets sent* — the one dangerous rsync flag combination in this repo exists in one place, and both `install.sh` and `deploy.sh` call it. `scripts/deploy.sh` is the single deploy path, and `./vpn deploy` is the only thing that calls it. `deploy.sh` deliberately does **not** bootstrap: on a server whose state directory has been damaged, generating fresh secrets would silently invalidate every profile already handed out, so `apply` fails loudly instead and points at `bootstrap` or a backup.

## Users

`users.json` is the source of truth across all protocols, at `SCHEMA_VERSION` 2 — the version that added `dnstt_password`. `user add` validates the name (`[A-Za-z0-9._-]`, 1–32 chars, starting with a letter or digit): `render_ikev2_env` joins names and passwords into two **space-separated** env vars, so a name with a space would misalign the lists and hand one user another's password. `render` makes the same check again on whatever the file holds, for the reason given under the registry.

`validate_name` also **rejects the names the dnstt-sshd base image already ships** — `root`, `mail`, `sshd`, `nobody`, `wheel`, `tunnel` and the rest of `alpine:3.20`'s `/etc/passwd` and `/etc/group`, plus a handful of standard `adduser` reservations that are not in this particular image, because the base tag can move and a rejected name costs one person one retry while the failure it prevents is silent. Case-folded, because `find()` already treats names case-insensitively, so allowing `Root` would only allow the same collision with a different spelling.

```bash
./vpn user add <name>        # fresh credentials for every protocol
./vpn user rm <name>         # permanent
./vpn user enable|disable <name>
./vpn user list [--show-secrets]
./vpn user export <name> [--protocol <p>] [--qr]
```

**IKEv2 is reconciled, not remembered.** `vpnctl ikev2 reconcile` diffs `ikev2.sh --listclients` against the enabled users on every apply and repairs both directions, writing `ikev2_provisioned` from observed truth. If `--listclients` *fails*, reconcile aborts rather than reading the empty result as "nobody has a certificate" — that reading would try to re-issue every user, fail on "already exists", and then record that nobody is provisioned while the certificates kept working. When a revocation can't run because the container is down, the name goes into `state.json`'s `revoke_pending` — the intent outlives the deleted user record, so a `user rm` with ikev2 stopped can't leave a working certificate behind with nothing to retry it.

**A pending revocation used to be dropped the moment its name became wanted again, which handed the next holder the previous holder's certificate.** All ordinary commands, no error anywhere: `protocol off ikev2`, `user rm alice` (queues the intent, certificate untouched by design), `user add alice` — a different person under a reused name — then `protocol on ikev2`. Reconcile skipped the revocation because `alice` was wanted, found `alice` still in `--listclients` so issued nothing, wrote `ikev2_provisioned=True` from that observation, and emptied the queue because the name had never entered `failed`. The new holder's profile was the previous holder's key pair, `--exportclient`'s `.p12` has a verified **empty** password, and the removed holder's own exported profile went on working too. A name now leaves `revoke_pending` only when its own removal succeeded, or when there was nothing left to remove — **never because it became wanted**; a queued name that is wanted again is revoked and then re-issued.

**A `revoked` certificate was also counted as present.** So a user who was revoked and is wanted again was never re-issued and *was* recorded as provisioned: a profile that cannot connect, written down as working. `ikev2ctl.parse_clients` is a pure function in the module that already hard-codes this image's CLI contract, and it splits the listing into two sets — `valid`, what a client can actually connect with, and `reserved`, a name the IPsec database still holds for a certificate that cannot. A reserved name is deleted before it is re-added, which is one step of the ordering `remove_client` already documents. A queued name the container holds in neither set (a lost volume, a restore from a backup older than the certificate) has nothing to revoke and leaves the queue, because retrying it for ever would put a permanent failure in every apply's payload for a name that exists nowhere.

Both of those survived for one reason worth recording: `cli.apply()` was called by zero of 334 tests, and `reconcile_ikev2` — the only writer of `ikev2_provisioned` and the only drainer of `revoke_pending` — by none either.

Hard-won IKEv2 facts: there is no `--removeclient`. `--deleteclient` alone does not stop a certificate working (the image says so itself); `--revokeclient` does, but leaves the name reserved so a later `--addclient` fails with "already exists". `remove_client` does both, in that order, each with `-y` or they block on a prompt. Re-enabling a user issues a **brand-new certificate** — the old profile stops working and needs re-exporting.

`--exportclient` writes three bundles: `.p12` (Windows/Linux), `.sswan` (Android/strongSwan), `.mobileconfig` (iOS/macOS, a complete ready-to-import profile). It writes them into `/etc/ipsec.d`, which is the persistent volume — so they survive restarts *and ride along in every backup*. `export_client` reads them out as bytes and then deletes them, which is what makes the old `exports/` problem actually go away rather than move. **Verified: the `.p12` has an empty password** — it is an unprotected private key, so whoever holds the file has VPN access. That is why `vpn share` is single-use, LAN-only and short-lived.

Recreating the ikev2 container drops **every** session it serves — L2TP, Cisco IPsec and IKEv2 alike. Certificates survive (they're in the volume); tunnels don't.

## IKEv2 client connectivity: the client's ISP filters IKE by payload shape

Clients cannot connect, and **it is not the server**. Privileged mode was tried and reverted (the commits "Temporarily switch ikev2 to privileged mode for diagnostics" and "Revert ikev2 to non-privileged mode" — named by subject, because a hash in prose does not survive a history rewrite and the two this sentence used to cite were replaced for exactly that reason); a full bare-metal `hwdsl2/setup-ipsec-vpn` install was also tried. Re-measured properly on 2026-09-08, and the mechanism is now known exactly.

**A DPI middlebox inside the client's ISP (Rostelecom) drops UDP datagrams whose payload parses as an ISAKMP header, when they are addressed to a foreign destination.** Domestic destinations are exempt. It is not the hosting provider, not `pluto`, and not anything in this repo.

The measurement that settles it, and the one to repeat if this is ever doubted — send probes with **TTL=3**, so they expire inside the ISP core and *cannot* have reached the destination, then vary only the destination address:

| destination | genuine `IKE_SA_INIT` | same-size junk |
| --- | --- | --- |
| this server (SE) | **0/3 — dies before hop 3** | 3/3 |
| `8.8.8.8`, `1.1.1.1`, `9.9.9.9`, `185.199.108.153` | **0/3 each** | 3/3 each |
| `194.87.49.94` (Timeweb, RU-owned) | 3/3 | 3/3 |
| `77.88.8.8`, `213.180.204.242` (Yandex) | 3/3 | 3/3 |

Google, Cloudflare, Quad9 and GitHub plainly do not run IKE filters, and could not have dropped a packet that expired ten hops short of them. So the decision is made on the *client* side, keyed on payload shape × destination. `bash scripts/diagnose-ikev2.sh path <ip>` reproduces the localisation for one destination; run it a second time against a host you know answers IKE to show the filter is keyed on destination. The port sweep and the priming result below were separate measurements, not something that command reproduces.

Three properties that decide what is and is not worth trying:

- **It is stateful, and the first packet of a flow decides.** A real client's first packet *is* the `IKE_SA_INIT`, so it is dropped and that 5-tuple is then poisoned — 200 retransmits produced zero replies. Prime the same tuple with one junk datagram first and the byte-identical `IKE_SA_INIT` sails through and `pluto` answers it in full. That is why `docker logs ipsec-vpn-server` contains **zero** IKE negotiations ever and `ipsec trafficstatus` is empty: the server has never been allowed to hear a client, not once.
- **It is destination-port-independent.** IKE payloads are dropped on 53, 443, 1701, 12345 and 51820 alike, while same-size junk arrives on every one. **Moving IKEv2 to a non-standard port cannot work** — do not spend time on it.
- **It applies identically over IPv6.** Not a NAT or CGNAT artifact.

What actually helps: connect from a different ISP (expected to work outright, and the one claim still untested — there was no third vantage point); or use VLESS-REALITY / Hysteria2, which are unaffected on this same network and are what this stack already does well; or move the endpoint to a prefix the filter does not act on, which is precisely why a comparison box on Timeweb answers IKE while this one does not.

**Why the old conclusion said "settled" and pointed at the client anyway.** It reached the right suspect for the wrong reason, on evidence that could not support it. `scripts/diagnose-ikev2.sh probe` sent a plain `DIAGPROBE-<host>` datagram — junk, the exact shape this filter passes — and its arrival was read as "the provider is not blocking, so blame the client". Against a provider that really did block inbound IKE, that same test would have said the same thing and been flatly wrong. **A junk datagram on port 500 is not a proxy for IKE.** `probe` now sends a real `IKE_SA_INIT` plus a separately-marked junk control, so `listen` reports *which shape* arrived, and `path` localises the drop without needing a second host at all.

**The FORWARD rules** (`ikev2ctl.ensure_ipv4_forwarding`) are a separate, real failure mode. IKEv2 IPv4 clients are assigned from the image's `XAUTH_POOL` (`192.168.43.10-192.168.43.250` by default, inside `XAUTH_NET` — *not* from `L2TP_NET`, `192.168.42.0/24`) and, unlike L2TP, have no ppp interface, so without a `net0`↔`net0` accept pair the SA establishes and no traffic forwards, silently. `run.sh` does add that pair, but its idempotence guard tests a rule in the **nat** table while the accepts live in **filter**, so anything clearing filter alone loses them with nothing to restore them. This is why `vpnctl` needs root, and why `vpn-stack.service` (oneshot, `After=docker.service network-online.target`) re-applies them at boot — raw `iptables -I` inserts with no persistence of their own.

The ensure runs from `apply`'s **`finally`**, and both halves of that matter. It used to sit at the end, after every step that can `die()`, so a converge failure skipped it silently — and these inserts are the difference between an IKEv2 SA that forwards traffic and one that establishes and carries none. It also runs *after* `firewall.reconcile`, which the `finally` guarantees, because `ufw allow` reloads ufw's own rules and the raw inserts have to come last.

**The rules are removed when ikev2 is turned off.** Nothing used to take them back out, so `protocol off ikev2` left two raw inserts in FORWARD with no owner, no persistence and no protocol behind them — indistinguishable, to the next person reading the chain, from a rule somebody meant. One function owns the whole question "do the FORWARD rules match the enabled set", so a converge failure cannot skip either direction. Removal deletes while `-C` still matches, up to a bound rather than a `while True`, because the image's own `run.sh` installs the identical pair and identical rules are indistinguishable to iptables: there is no owner to compare against. Removing the image's copy too is acceptable exactly here — the container it belongs to is going away and reinstalls its own pair the next time it starts. The pool can only be asked of a *running* container, so by then the answer is usually the image default, and a server with a custom `VPN_XAUTH_POOL` keeps its rules with `-C` saying so by not matching.

**IKEv2 over IPv6 is deliberately out of scope.** The pool's IPv6 half (`fddd:500:500:500::1000-…` on a stock image) gets no `ip6tables` pair, so an IPv6 IKEv2 client depends entirely on the image's own rules. That is stated rather than implied because the alternative — a parse that quietly drops the half it cannot handle — is the shape of the bug this whole area already had once.

That subnet was hardcoded as `192.168.42.0/24` until 2026-09-08, which is the L2TP pool: every rule `vpnctl` installed protected addresses no IKEv2 client is ever given, and **both** health checks (`scripts/smoke.sh`, `scripts/diagnose-ikev2.sh`) asserted the same wrong subnet, reporting green in exactly the failure they exist to catch. All three now ask the container which pool it hands out — `conn ikev2-cp`'s own `rightaddresspool` first, because that is literally what `pluto` assigns, then `VPN_XAUTH_NET`, then the image default — rather than trusting a constant. The order matters: `run.sh` uses `XAUTH_NET` for its *firewall* rules while `ikev2.sh` builds the pool from `XAUTH_POOL`, so preferring the net would reproduce this very bug for anyone who set only one of them. Same principle as IKEv2 certificates: reconcile from observed truth. Either source failing falls through to the image default and the **provenance** then says which one failed, because a default that reads like an answer is the shape of the original mistake.

**The sequel is that three copies agreeing is not the same as three copies agreeing exactly.** `vpnctl.ikev2ctl`, `scripts/smoke.sh` and `scripts/diagnose-ikev2.sh` each derive this value, and each now derives the covering network from the pool's **first and last** address rather than assuming a `/24` on the first. A pool of `192.168.43.10-192.168.44.250` straddles a boundary: calling it `192.168.43.0/24` makes `vpnctl` install its accepts for one range while a health check goes looking for a rule on another, finds none, and reports a healthy box broken — the same failure as the original constant, wearing the shape of a fix. Wider is the safe direction, since an address inside the covering network but outside the pool is one `pluto` never assigns. Verified byte-identical between the shell and the Python for the image default, a straddling range, a bare CIDR, an invalid octet, an IPv6 pool and the empty string. All three validate the value before handing it to `iptables`, and validate the *address* rather than its shape: `192.168.256.0/24` used to pass a shape test and then make `iptables -C` fail in a way indistinguishable from "the rule is missing" — reporting a healthy box as broken, which is the exact case the comment beside it claimed to prevent.

## Deployment

`./vpn deploy` → `scripts/deploy.sh root@<host>`.

**Neither workflow deploys, deliberately.** `.github/workflows/ci.yml` runs ruff, the Python test suite, `bash -n` over every shell file, and both Dart suites; `.github/workflows/app.yml` builds the client. Neither holds a secret, declares an `environment:`, has an ssh or rsync step, or can reach a server, and both write `permissions: contents: read` out rather than inheriting it from a settings page a workflow cannot document. That is the actual invariant; "no CI at all" was the older, blunter version of it, and asserting it of `ci.yml` alone was the version that had stopped covering the tree — `app.yml` is nine-plus jobs that hand five artifacts to humans and build sing-box from source twice. Deploy-on-push bought nothing here — one operator, one laptop, one command — and cost a standing credential with root on the VPN server held by GitHub, plus a live server mutated by every `git push`. That is not a theoretical objection: a push did exactly that to a server that had just been deliberately wiped. One loose end neither workflow can close: `DEPLOY_HOST` and `DEPLOY_SSH_KEY` outlived the workflow that used them and still sit in the repository's Actions secrets with nothing in this tree referencing them. A workflow cannot delete a repository secret; delete them in the settings page.

**Pinned now means pinned to a commit SHA**, with the tag in a trailing comment, in both workflows. It used to mean a major tag, which is a mutable pointer — `@v4` is whatever its owner last moved it to, and for the third-party `subosito/flutter-action` that owner is not GitHub. A workflow that builds the VPN clients this project hands to humans, on a runner holding a checkout of this tree, is not a place to accept whatever is there today. The cost is that a SHA cannot tell you it is stale, which is what `.github/dependabot.yml` is for: the bumps arrive as pull requests a human reads, the same shape as everything else here. Two things a reader should know before wondering why no pull requests arrive — Dependabot reads that file from the repository's **default branch only**, and GitHub's own actions are grouped so the next Node-migration-shaped change is one diff rather than five. The Node 20 deprecation travelled in the same change as the pinning, and had to: a SHA freezes the runtime too, so a major tag would at least have drifted onto a supported runtime eventually and a SHA never does.

The rsync (in `scripts/push.sh`) uses `--filter=':- .gitignore'` and `--delete`, and **not** `--delete-excluded`. The pairing is the point: without `--delete`, a file deleted from the repo lives on for ever on every server ever pushed to — `scripts/host-bootstrap.sh` was removed here and is still sitting in `/opt/vpn-stack` on boxes pushed before it went, executable, one command away from re-running a provisioning step that matches nothing. `--delete-excluded` has the opposite meaning and would delete **from the server** the very files the filter exists to protect: `/opt/vpn-stack/.env`, the symlink into the state directory, any rendered fragment, any cert. Excluding means "do not send", never "remove there". It also passes `--chown=root:root`, because `-a` preserves the *operator's* uid and gid and this lands a tree root executes: on a laptop whose user is 1000, `/opt/vpn-stack` came out owned by uid 1000, which on the server is either nobody or some other account entirely — and that account can then rewrite the code `vpnctl` runs as root. `app/` and `notes/` are excluded by path rather than left to `.gitignore`, because the app is tracked and a VPN server has no use for ten thousand lines of Dart. Then `uv sync --frozen`, `vpnctl apply`, `scripts/smoke.sh`.

`scripts/install.sh` takes a bare Ubuntu 22.04/24.04 box to a serving VPN in one command, across several separate SSH sessions rather than one long heredoc — the firewall step has to prove a *fresh* connection still works before disarming its own safety net, and it cannot do that from inside the connection it might be about to sever. That reason is the durable one; the session count moves whenever the steps do, and it moved when the server-local half became `scripts/provision-host.sh`.

**`install.sh` pushes this checkout; it does not clone** — but the reason changed on 2026-09-11 and the old one is worth retiring by name. It used to be that the repo was private, so a clone needed a deploy token just to install. The repo is public now and a clone needs nothing. What `push.sh` still buys is that rsync sends the **working tree**, uncommitted changes included, which a clone cannot; that is what makes `./vpn deploy` useful while you are editing.

The app takes the other route: it has no checkout to push, so it clones the public repo onto the box. That was a supply-chain decision written down as one — an app-provisioned server executed whatever was on `main` at that instant, unpinned. It now clones a **tag**, so the server-local half it runs is a reviewed tree; bumping `ProvisionConfig.repoRef` is how the app adopts a new server tree, and it is the one line to change for that. The clone also asserts that `scripts/provision-host.sh` exists in the fetched ref and names both, because the branch default had a second failure nobody would have guessed from the symptom: that script is a pure addition on this branch and does not exist on `main`, so every app-driven provision cloned cleanly and then died at exit 127 on its first host stage, on a box whose apt and git had already been touched.

**The server-local half is `scripts/provision-host.sh`**, extracted so it has one definition and two callers. `install.sh` pipes it over stdin for the `base` stage (that stage is what installs `git` and `rsync`, so no delivery mechanism has run yet) and runs it from the pushed checkout for `code`. The app runs the same script. The split is `base` (docker, state dir, sysctls, `/dev/ppp`, boot unit) and `code` (`.env` link, `uv sync --no-dev`, the shim, `bootstrap`) — two stages and not one, so the firewall proof can sit between them: a keyring minted on a box you have just locked yourself out of is a server that has to be rebuilt.

The ufw **deadman** is real, not decorative: a detached `setsid` timer that disables ufw unconditionally after 180s, armed before the first `ufw enable`, disarmed only after a brand-new SSH connection — one that had to pass through the new rules — succeeds. It records its own pid rather than trusting `$!` (setsid forks when the caller is already a process-group leader) and is killed by process group, so the `sleep` goes with it. Arming now **reaps or refuses** on finding a live predecessor: a re-run after a transient failure used to orphan the first timer, which then ran `ufw --force disable` possibly *after* the installer had printed success. The disarm is a checked sequence rather than two kills with their stderr discarded behind a trailing `; true` that `set -e` could not see, and it exits non-zero if the timer is still breathing afterwards, so `set -e` stops the install there rather than handing back a box whose firewall turns itself off minutes later.

**Which port to open is asked, not assumed.** `install.sh` hardcoded `ufw allow 22/tcp`, so `./vpn init` could never complete against an sshd on another port: ufw came up with only 22 open, the fresh-connection proof failed, the script exited 1, the deadman restored access 180 seconds later, and the identical re-run failed identically with nothing in the output mentioning the port. `ssh_ports_to_allow` takes the port this session came in on (nothing is more direct — it is the port that has to keep working, and it just demonstrably did) plus **every** port `sshd -T` names, which sees a `Port` in an `Include` or an `sshd_config.d` drop-in that grepping `sshd_config` does not; 22 only as a last resort, for the case where both sources were unreadable. Every rule it adds is tagged `vpn-stack:ssh`, which is the tag `firewall.reconcile` protects by name.

Two things a fresh box needs that an established one hides: `uv` installs to `/root/.local/bin`, which is **not** on the PATH of a non-interactive SSH session or a systemd unit, so it is symlinked into `/usr/local/bin` (only when nothing is already there) and the `vpnctl` shim sets its own PATH; and `/dev/ppp` must exist at container-create time.

Docker is installed from **Docker's own apt repository**, not `curl https://get.docker.com | sh`: same packages, but signed, upgradable with the rest of the system, and readable before it runs. That repository is behind CloudFront, which returns **403 over IPv4** to some ranges while serving the same bytes over IPv6 — observed on this host. `install_docker` probes both families, uses whichever answers, and when it has to use IPv6 it persists `Acquire::ForceIPv6` in `/etc/apt/apt.conf.d/99-vpn-stack-ipv6`, because otherwise the operator's own next `apt update` fails on that repository. If the system mirror turns out to have no IPv6, it reverts both files rather than leaving apt broken. (Note the asymmetry: `ghcr.io`, where sing-box comes from, answers over IPv4 and *not* IPv6. Both families are load-bearing.)

**Everything already installed is left alone.** docker, git, rsync, ufw, iptables and uv are each guarded by `command -v`, and the script says so rather than staying silent. If you install docker yourself it touches neither the daemon, `/etc/docker/daemon.json`, nor apt. ufw is only `enable`d when it was inactive, and `firewall.reconcile` only ever reads and writes rules carrying a `vpn-stack:` comment.

**The ssh rule is protected by its tag, not by the number 22.** `firewall.SSH_RULE` was the literal `"22/tcp"` and the removal loop's exemption compared against it — but `current_tagged()` claims every rule commented `vpn-stack:*`, `desired()` is built from the protocol registry, and no protocol is called `ssh`, so an ssh rule on any *other* port was always in `have` and never in `want`. The app's provisioner writes `ufw allow "$port"/tcp comment 'vpn-stack:ssh'` with an operator-settable port, so the first converging apply on such a box — the one its own `user add` runs — issued `ufw --force delete allow 2222/tcp` against an active default-deny firewall, with the install deadman long since disarmed because the firewall step had legitimately succeeded. Recovery needed the provider's console. The invariant was never the port; it was *the door we came in through*. The exemption keys on the parsed tag and keeps the literal only as a second condition, and `desired()` now refuses outright to build a rule set from a protocol named `ssh`, so the one tag the removal loop will not act on cannot also be claimed by the registry. The add path no longer silently adopts an identical hand-added untagged rule either — adopting it makes this tool believe it owns a rule a human opened, and the next `protocol off` deletes it.

### Verified end to end on a bare box

Ubuntu 24.04.1, 2026-09-06, from `docker`-only to serving: install, `user add` (IKEv2 certificate issued by reconcile), export of all three bundles, `protocol off ikev2` → `on` (certificate survived the volume), `deploy`, **reboot** (boot unit re-applied the FORWARD rules, both containers returned, ufw persisted), and a backup/restore round trip. From outside, `10443/tcp` presents a genuine `www.apple.com` EV certificate and a port ufw does not allow is filtered.

## The app

`app/` is a Flutter client that provisions a server and connects to it — Android, iOS, macOS, Windows, Linux, one Dart codebase. It exists because the CLI needs a laptop, a shell, an SSH key and `./vpn`, and somebody who just wants a working tunnel has none of those. `app/README.md` is its own document; what belongs *here* is the part that changes how the server has to be treated.

**It is a third operator, and it holds root SSH.** `./vpn` on your machine, `vpnctl` on the server, and now an app on a phone running the same `vpnctl` over the same lock. That is why `vpnctl` takes `/run/vpn-stack.lock` itself rather than trusting each caller (see "Where things run"), why `flock -E 75` is the app's wrapper and 75 is a documented exit code rather than an accident, and why `firewall.reconcile` protects the ssh rule by tag: every one of those was a bug the app either created or would have hit first.

**It is not a second implementation of the server.** The server keeps every decision it owns — ports, secrets, rendering, share links. The app asks questions and renders answers. `render` and `share` in `vpnctl/protocols/` are pure functions and the temptation is to port them to Dart for offline use; don't. Two implementations of a credential format drift, and the drift is invisible until somebody's profile stops importing. `lib/config/` is the one layer that might look like that duplication and is not: it *consumes* a URI, and the sing-box schema version belongs to the client's engine rather than the server's.

**The `--json` contract is pinned by a generated fixture corpus, and that was bought late.** `app/README.md` gives the app's presence in this repository as the reason a breaking `--json` change cannot land unnoticed — and for a while it could. The Dart payloads were hand-typed from what somebody remembered `cli.py` printing, nothing compared the two, and renaming a key left both suites green while the failure surfaced on a phone. Three of those transcriptions were **already wrong** and all three parsed: an export fixture carrying `failed: ["hysteria2"]`, which only a `share_via_container` protocol can produce; IKEv2 bundles named `kate.p12` where the container writes `kate-ikev2.p12`, the suffix `bundle_label` matches on; and a dnstt card with four fields where `share()` emits two cards of five and three. The tests were passing against a payload no server can send.

So the fixture is now the shared artifact. `tests/test_json_contract.py` drives `cli.py`'s real `cmd_*` functions under `VPN_STATE_DIR` and holds each payload to a file under `app/test/fixtures/`; the Dart suite reads those same files. A rename fails pytest, and regenerating the golden without touching the app fails the Dart parse. Two details are the difference between that and a decoration. The comparison is on the **serialised text**, not the parsed object, because two dicts compare equal across a reordering and the order is not free — the app decodes into an order-preserving map, so a protocol's position is the order `ShareBundle` offers its URIs to a tunnel engine; measured, moving a key in `cmd_status` left all 21 tests green under dict equality and red on the line comparison. And the corpus is **walked** as well as read per-command, so each fixture must be given a reader, declared a refusal, or listed with a reason — a per-command list only reaches the fixtures somebody remembered to name. Deliberately *not* a regex over `models.dart`: `app/README.md` rejects that option by name, and a Dart parser written in Python would pass on a model that compiles and refuses every real payload. `ApplyResult`'s tolerance of unknown keys stays — it is what lets `apply` grow a field without breaking an installed app — but the test pins which unknowns are expected, so the carve-out cannot quietly become a blind spot.

**`app/ios/` is committed, and it is the one exception in `.gitignore`'s five platform directories.** `flutter create` cannot produce what is needed: an `NEPacketTunnelProvider` is a separate app-extension target with its own bundle identifier, entitlements and an App Group, and none of that survives regeneration — a regenerated project has no tunnel in it and nothing to sign. `app/tool/ios_project.rb` is how the project is produced, `app/ios/.gitignore` keeps the per-machine files out, and `app.yml` picks between an `ios` job and an `ios_project` job on whether the directory is committed. The route to regenerate it is one gesture in git: delete `app/ios/` and push; `ios_project` uploads a replacement for a human to commit. There is deliberately no `workflow_dispatch` button, because GitHub only offers one for a workflow present on the **default** branch and this file lives on `app` — an input that does nothing reads as a supported route. A third job, `ios_result`, fails unless **exactly one** of the two succeeded: a skip is not a failure, so for a while neither one running looked exactly like success.

**`app/tool/ios_identifiers.sh` is the single definition of the App Group identifier and both bundle ids.** Four places must agree — two `Info.plist` keys, both entitlements, the extension's bundle id and the generator's own tables — and every one of those strings is compared at **runtime** by iOS and by nothing at build time. A mismatch between the App Group in an entitlement and the App Group in an `Info.plist` compiles, links, signs and ships; the symptom is a sandbox denial on the first connect, on a target that has never been signed. `tool/check_extension.sh sources` asserts the tree against that file and `ios_project.rb --check` asserts the generator against it, both in the cheap ubuntu job, because reading the strings is the cheapest available substitute for a device. It is shell rather than Ruby precisely so the ubuntu job can source it — and being sourced means it has no shebang, which is how `ci.yml`'s "every shell script" job managed not to parse the single definition of the App Group for a while. That finder now matches `*.sh` by name **and** anything with an sh shebang, because either rule alone misses one of the two kinds of shell file in this tree: 12 files before, 13 after.

**The app provisions from a tag, not a branch.** See "Deployment" for the two reasons — a reviewed tree instead of whatever landed on `main`, and a `main` that does not contain `scripts/provision-host.sh` at all. The firewall step is the one part that cannot move to the server, and it is reimplemented in Dart rather than shared: a script running on the box cannot prove from inside one connection that a *different* connection would survive rules it is about to install. The prover has to be somewhere else. Everything else in the server-local half is `scripts/provision-host.sh`, called by the app exactly as `install.sh` calls it.

**Nothing native has ever carried a packet, and that is the honest limit of what a green build proves.** There is no macOS and no Android SDK on the machine this was written on, so `app.yml` is the first thing that ever compiles the ~2,300 lines of Swift or the ~1,950 of Kotlin under `app/packages/singbox_tunnel/`, and no device has run either. The five artifacts are unsigned by design, not by omission: the `.ipa` is `--no-codesign` and installs nowhere until somebody with an Apple *organization* membership signs it (Review Guideline 5.4, applied at notarization, and a free Apple ID has no Network Extension entitlement at all), the macOS `.app` and the Windows `.exe` trip Gatekeeper and SmartScreen, and the APK carries Flutter's debug key. Do not add signing steps and do not add placeholder secrets for signing — an empty secret a step reads is how a workflow starts silently producing unsigned output while claiming otherwise. What *is* checked is everything that can be: both Dart suites run in `ci.yml` with no path filter, `flutter analyze` is fatal on every diagnostic down to an info (flutter's wrapper defaults `--fatal-infos` and `--fatal-warnings` to on, and what stops `flutter_lints`' next release vetoing every branch is the committed lockfile, enforced with `--enforce-lockfile`, not a flag), and `check_extension.sh bundle` asserts the built `.app` actually contains the extension — because a stock one-target Flutter project builds clean, links no libbox, contains no `NEPacketTunnelProvider`, and wraps into a perfectly valid `.ipa`.

`app/packages/singbox_tunnel/` holds the platform code, and it is a package rather than `app/android/` because those directories are regenerated. Its 38 tests are the state machine whose worst failure is reporting "Connected" with no tunnel, and for a while **nothing ran them**: `flutter test` runs with working-directory `app/`, which collects `app/test/` and never descends into `packages/`. Both `ci.yml`'s `dart` job and `app.yml`'s `check` job run it now. The engine is `sing-box`, built from source by two Go jobs — `libbox.aar` for Android, `Libbox.xcframework` for Apple — at the version read out of `compose.yml`, the same line that pins the server's image, so one number governs the engine at both ends of a configuration. `libbox` is published nowhere; sing-box's v1.14.0 release carries 167 assets and not one `.aar`.

Three failures in the app worth keeping because they are the same shapes this repository has met on the server. A schema error rendered up to 1200 characters of the raw payload into its message, and for `user export` that payload reliably **begins with a working VLESS URI** — so the text a person pastes into a bug report carried their credential; `raw` stays on the exception for programmatic use and the human message is built from structure with secret-bearing values redacted. The sing-box config the iOS extension runs — carrying a VLESS UUID or a Hysteria2 password — was written into the App Group container and never deleted, and `removeFromPreferences` appeared nowhere in the repository, so deleting a server in the app left iOS Settings listing a VPN profile that, toggled, started the extension from the persisted credentials; the file goes on a user-initiated stop and when its profile is removed, the last profile's removal takes the preferences with it, and the container is excluded from backup so a credential does not ride into iCloud. Android had the mirror-image problem from the other side: the configuration existed only in the start Intent's extras, so when the *system* started the service — always-on VPN, or a restart after reclaiming it — the config was null and the message asserted a plugin bug; it is persisted in the app's private files directory and **deleted on a user-initiated stop**, so a disconnect does not leave a credential on disk that the person believes is gone. None of the three revokes anything: only `vpn user rm` does, and the app's own dialog promises only a local removal.

## Conventions

- `paths.py` owns every path. Don't build one inline.
- **`dotenv.read()` strips matching quotes and a leading `export`, because `docker compose` does and `vpnctl` did not.** A quoted `VPN_DNSTT_ZONE` handed the container one zone and every share link another, with nothing reporting the mismatch. A trailing comment is still *not* stripped, which `provision-host.sh`'s own `.env` template relies on. `dotenv.set_key` had no callers and would have destroyed every comment in `/etc/vpn-stack/.env`, non-atomically; it is deleted.
- **Everything `render` writes is 0600**, decided by default rather than by filename. The mode used to be `0600 if the name ends in .key or .env else 0644`, and `dnstt-sshd/logins` ends in neither — so the plaintext list of every user's dnstt password was rendered world-readable, contained only by the 0700 parent. Same failure shape as an exact-path `.gitignore` rule. Nothing needs the wider mode: every rendered path is bind-mounted `:ro` into a container that reads it as root, and no service declares a `user:`.
- **A commit hash written into prose does not survive a history rewrite.** This file was breaking its own rule in four places: two hashes cited for the privileged-mode experiment, one for the committed-backup incident, and one in `.github/workflows/ci.yml`'s header for the removed deploy workflow. Every one of them stopped resolving — `git cat-file -t` says so — and each was still sitting there to be copied into a published document. All four now name the commit *subject*, which survives; the backup incident names none, because the commit that carried it was removed from history by `git filter-repo` and there is no subject left to name. Check any hash you find here with `git cat-file -t` before repeating it.
- Structural constants (ports, SNI, masquerade domains, bandwidth caps) live in the protocol modules, in git. They are no longer trapped in a gitignored file.
- `composectl.up` passes `--build`. Without it a changed Dockerfile or entrypoint is rsynced to the server and then silently ignored, because compose reuses the image whose tag already exists — so a fix appears to deploy and changes nothing.
- **Code can roll back; the database cannot.** `push.sh` will happily rsync an older checkout over a newer one, and it happened: deploying a stale tree onto a `users.json` that had grown a field killed every vpnctl command with `TypeError: User.__init__() got an unexpected keyword argument`. `load()` now refuses, by name, on an unknown field or a higher `schema_version`, and says the code is older than the database. It refuses rather than dropping the field, because ignoring it would let the next `save()` write the record back without a credential this code is merely too old to know about.
- `per_user` says whether a protocol issues a distinct credential per person. It must not gate *sharing*: filtering `user export` on it made the command silently return nothing for dnstt back when dnstt was shared. dnstt is `per_user=True` now, but the filter is still gone, and should stay gone.
- No device/connection limiting anywhere. sing-box has no native per-user cap (`SagerNet/sing-box#2579`, closed "not planned"); deliberately skipped at solo-user scale.
- `docker compose down -v` destroys both named volumes — every IKEv2 certificate, unrecoverable, and the dnstt SSH front's host key. Prefer `stop`/`restart`.
- `export.items_for` is gone. It had no callers and duplicated `cmd_user_export`'s loop while carrying two lessons — the `per_user` filter that must stay gone, and snapshot-versus-keyring — in the copy nothing executed. A lesson in dead code is not a check; both moved to where they are still true.
- `--json` is a public API and must stay parseable: it goes to stdout, everything else to stderr, and it is accepted in **any** position (`user export x --json` as well as `--json user export x`). `--qr` is suppressed under `--json` for the same reason — ASCII art in the middle of the payload broke `./vpn share`.
- `apply` returns `enabled_protocols`, not `enabled`. The two collided in `emit(**result)` and made `user enable`/`user disable` raise `TypeError` on every single invocation.
- **Tests live in `tests/` and need no server, no Docker and no root.** They cover the pure layer — `render`/`share` for all four protocols, `assert_ports_disjoint`, `users_store.load()`'s refusals and its never-writes property, `firewall.reconcile`'s diff (including a tagged ssh rule on 2222 and on 49222, both of which fail against the old exemption), `_is_bound` skipping loopback, `down_disabled`'s `None`-versus-empty distinction, the bootstrap set rule and its one derivable carve-out, `changed_services`' consumer table, `cli.apply()` and `reconcile_ikev2` end to end against a faked machine, `state.load`/`save`, `guard.require_server`, the XAUTH pool derivation pinned byte-identical between the Python and both shell copies, and the `--json` corpus both sides read. 491 of them, up from 202. They use `VPN_STATE_DIR` and `tmp_path`, so nothing reaches `/etc/vpn-stack`. Anything that needs a real container belongs in `scripts/smoke.sh`, which asserts against a live server; the two are not substitutes.

- `users_store.load()` never writes. It used to mint a fresh `l2tp_password` for any record missing one and save it, so a plain `user list` could silently rotate a live credential. Booleans get defaults because those are derivable; a missing *secret* is a damaged database and says so.
